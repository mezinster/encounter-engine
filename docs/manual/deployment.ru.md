# Установка

Как поднять свой экземпляр encounter-engine. Два пути, и начинать стоит с первого:

- **[Попробовать на своей машине](#попробовать-на-своей-машине)** — полчаса, ничего покупать не нужно.
- **[Боевая установка](#боевая-установка)** — свой домен, свой сервер, настоящие игры.

Руководство пользователя: [ru.md](ru.md). English version: [deployment.en.md](deployment.en.md).

Если сервер вам не нужен, а поиграть хочется — есть [общий сервер](https://game.mezin.eu/).
Установка нужна тем, кому нужен свой домен, свои правила и свои данные.

---

## Что это за приложение

Обычное приложение Ruby on Rails 8. Ничего экзотического: нет очередей задач, нет Redis,
нет фоновых воркеров, нет сборки фронтенда — статика отдаётся прямо из `public/`.
Один процесс `puma` и одна база данных.

| | |
|---|---|
| Ruby | 3.3.12 (зафиксирован в `.ruby-version` и `Gemfile`) |
| База | sqlite для разработки, PostgreSQL в бою |
| Почта | любой SMTP-сервер |
| Что должно быть снаружи | HTTP(S) на 80 и 443 |

Почта — не роскошь: команды собираются по приглашениям на e-mail, а пароль при регистрации
генерируется сервером и уходит письмом. Без работающего SMTP экземпляр формально запустится,
но пользоваться им будет нельзя.

## Попробовать на своей машине

Это путь «посмотреть, как оно устроено». Sqlite вместо PostgreSQL, письма никуда не уходят,
HTTPS нет.

**1. Ruby 3.3.12.** Ставится через rbenv. В неинтерактивных оболочках rbenv может не попадать
в `PATH` — тогда перед командами понадобится:

```bash
export PATH="$HOME/.rbenv/bin:$HOME/.rbenv/shims:$PATH"
```

**2. Зависимости и база:**

```bash
bundle install
bin/rails db:setup
```

`db:setup` создаёт `db/development.sqlite3` по `db/schema.rb`. Самих файлов базы в репозитории
нет — они создаются на месте.

**3. Запуск:**

```bash
bin/rails server
```

Приложение на `http://localhost:3000`.

**4. Первый пользователь.** Зарегистрируйтесь через форму на сайте: после регистрации вы сразу
залогинены.

> **Письма в разработке никуда не отправляются** (`config.action_mailer.delivery_method = :test`).
> Пароль, который сервер сгенерировал при регистрации, вы нигде не увидите — и в следующий раз
> войти не сможете. Задайте себе пароль из консоли:
>
> ```bash
> bin/rails console
> ```
> ```ruby
> User.find_by(nickname: "вашник").update!(password: "секрет", password_confirmation: "секрет")
> ```

**5. Сделайте себя администратором** — см. [Первый администратор](#6-первый-администратор).

**6. Тесты**, если хотите убедиться, что всё цело:

```bash
bundle exec rspec
bundle exec cucumber
```

## Боевая установка

Развёртывание — [Kamal 2](https://kamal-deploy.org/): образ Docker собирается, кладётся в
реестр и запускается на вашем сервере по ssh. Прокси, сертификаты Let's Encrypt и
переключение контейнеров Kamal берёт на себя.

### Что понадобится

| | |
|---|---|
| Сервер | Ubuntu, 1–2 vCPU, 2 ГБ памяти. Этого хватает на игру с десятками команд |
| Домен | и A-запись на IP сервера — **до** первого развёртывания, иначе Let's Encrypt не выдаст сертификат |
| Доступ | ssh по ключу, пользователь с правом `sudo` |
| Реестр образов | GitHub Container Registry, Docker Hub — любой |
| SMTP | адрес, порт, логин, пароль |
| На своей машине | Ruby с гемами проекта (`bundle install`) и Docker для сборки образа |

Порты 80 и 443 должны быть доступны снаружи. 5432 (PostgreSQL) — **не должен**: в
`config/deploy.yml` он публикуется как `127.0.0.1:5432:5432`, то есть виден только с самого
сервера. Не меняйте это на `0.0.0.0`.

### 1. Подготовка сервера

В `ansible/` лежит небольшой плейбук: ставит Docker, добавляет пользователя развёртывания в
группу `docker`, создаёт том для данных PostgreSQL и включает автоматические обновления
безопасности.

```bash
ansible-playbook -i ansible/inventory.ini ansible/playbook.yml
```

Впишите в `ansible/inventory.ini` свой хост. Обратите внимание: плейбук **намеренно не трогает
firewall** — предполагается, что фильтрацией занимается что-то снаружи (группа безопасности
облака). Если у вас это не так, откройте 22, 80 и 443 сами.

Всё то же самое можно сделать руками: нужен только Docker и пользователь, который имеет право
его запускать.

### 2. `config/deploy.yml`

Это конфигурация конкретного экземпляра, и она в репозитории заполнена под тот, что живёт на
`game.mezin.eu`. Поменять нужно вот что:

| Ключ | Что поставить |
|---|---|
| `service` | имя вашего сервиса (оно же — префикс имён контейнеров) |
| `image` | `ваш-аккаунт/encounter-engine` |
| `servers.web` | IP или имя вашего сервера |
| `proxy.host` | ваш домен. Можно несколько через запятую — сертификат будет выпущен на каждый |
| `registry.server` / `registry.username` | ваш реестр образов |
| `ssh.user` | пользователь для развёртывания |
| `env.clear.APP_HOST` | **один** домен — тот, что попадёт в ссылки в письмах |
| `env.clear.TZ` | часовой пояс сервера, например `Europe/Vienna` |
| `env.clear.DEFAULT_LOCALE` | язык по умолчанию: `ru`, `en`, `uk`, `ka`, `tr`, `be` или `pl` |
| `env.clear.SMTP_ADDRESS` / `SMTP_PORT` | ваш SMTP |
| `accessories.db.image` | образ PostgreSQL (см. ниже) |
| `accessories.db.host` | тот же сервер |

Два места, где легко ошибиться:

- **`proxy.host` — единственный источник правды о доменах.** Kamal перестраивает таблицу
  маршрутов при каждом развёртывании, и домен, добавленный руками на сервере, тихо исчезнет при
  следующем деплое.
- **`APP_HOST` — один домен, а не список.** Из него собираются абсолютные ссылки в письмах.
  Приложение может отвечать на нескольких доменах, но письма должны звать в одно место.

### 3. База данных

`accessories.db` поднимает PostgreSQL рядом с приложением, на том же сервере, с данными в
именованном томе Docker.

Образ собирается из `Dockerfile.postgres`: это стандартный `postgres:16` плюс
[wal-g](https://github.com/wal-g/wal-g) для непрерывного резервного копирования и настройки под
маленький сервер. Ничего специфичного для конкретного облака в самом образе нет — куда
складывать копии, определяют переменные окружения (`WALG_*`). wal-g умеет S3, Azure Blob, GCS и
файловую систему.

Если резервные копии вам пока не нужны, можно взять обычный `postgres:16` — приложение о wal-g
ничего не знает. Только имейте в виду, что база с результатами игр без копий живёт до первой
серьёзной ошибки.

Приложение соединяется с базой **по имени контейнера** (`<service>-db`), а не по `127.0.0.1`:
контейнеры стоят в одной сети Docker, и loopback внутри контейнера приложения ведёт в него
самого, а не в базу.

### 4. Секреты

Значений секретов в репозитории нет и быть не должно. `.kamal/secrets` только **называет**
переменные, а берутся они из окружения того, кто запускает развёртывание:

```
SECRET_KEY_BASE=$SECRET_KEY_BASE
```

Что нужно передать:

| Переменная | Что это |
|---|---|
| `SECRET_KEY_BASE` | ключ, которым подписываются cookies сессий |
| `POSTGRES_PASSWORD` | пароль пользователя базы |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | учётные данные почты |
| `KAMAL_REGISTRY_PASSWORD` | токен реестра образов |

`DATABASE_URL` и `MAIL_FROM` в `.kamal/secrets` **собираются** из перечисленного выше, а не
задаются отдельно — чтобы пароль базы и почтовый адрес существовали ровно в одном месте.

Правила, которые лучше не нарушать:

- **`SECRET_KEY_BASE` генерируется один раз** (`bin/rails secret`) и дальше не меняется. Смена
  разлогинивает всех разом. В production у него **нет** запасного значения: без переменной
  приложение не стартует — это сделано намеренно, чтобы в публичном репозитории не появилось
  «временного» ключа по умолчанию.
- **Значения — только в окружении.** Файл с `chmod 600`, который подхватывает ваша оболочка,
  или менеджер паролей, или секреты CI. Не в конфиге, не в истории команд, не в переписке.
- Если секрет всё-таки где-то засветился — **отзовите его**, а не «поменяйте потом».

### 5. Первое развёртывание

```bash
bundle exec kamal setup
```

`setup` ставит на сервер всё нужное, поднимает базу, собирает и выкладывает образ, запускает
приложение и получает сертификаты. Дальше — обычное:

```bash
bundle exec kamal deploy
```

Миграции применяются **сами**, при старте контейнера (`bin/docker-entrypoint` вызывает
`db:prepare`). Отдельного шага для них нет, и на первом развёртывании схема создаётся с нуля.

Здоровье приложения Kamal проверяет по `/up`. Пока этот адрес не отвечает, трафик на новый
контейнер не переключается.

Полезное:

```bash
bundle exec kamal app logs -f      # логи
bundle exec kamal app exec -i "bin/rails console"   # консоль
bundle exec kamal rollback         # вернуться на предыдущий образ
```

> `kamal rollback` откатывает **образ, а не базу**. Если в откатываемом релизе была миграция,
> удалявшая или переименовывавшая колонку, старый образ на новой схеме не заработает. Это общее
> свойство такого развёртывания, а не особенность этого приложения.

### 6. Первый администратор

Прав администратора нет ни у кого, пока их не выдали, а выдавать их может только другой
администратор. Первого приходится назначать из консоли:

```bash
bundle exec kamal app exec -i "bin/rails console"
```

```ruby
User.find_by(nickname: "вашник").update!(is_superadmin: true)
```

Дальше всё делается из интерфейса: раздел «Администрирование» в левом меню.

Две вещи, о которых стоит знать заранее:

- **Последнего администратора нельзя разжаловать** — ни через интерфейс, ни из консоли.
  Экземпляр не должен остаться без управления.
- **Назначение из консоли не попадает в журнал действий.** Журнал ведёт веб-приложение, а
  консоль работает мимо него. Это единственная дыра в журнале, и она неустранима.

### 7. Резервные копии

Если вы собрали образ PostgreSQL из `Dockerfile.postgres`, сервер уже пишет WAL-архив
непрерывно (`archive_command = 'wal-g wal-push %p'`), но **базовые копии** нужно снимать по
расписанию — из архива WAL без базовой копии не восстановишься.

В `ops/host/` лежат готовые systemd-таймер и сервис, которые делают это на самом сервере, а не
внутри контейнера — контейнер базы Kamal пересоздаёт при каждом развёртывании, и расписание
внутри него исчезло бы при следующем деплое.

Порядок восстановления — [`docs/runbooks/restore.md`](../runbooks/restore.md). Главное оттуда:
**сначала восстановите в отдельный контейнер и посмотрите, что получилось**, и только потом
трогайте боевую базу. В `ops/` есть скрипты для обоих шагов.

### 8. Обновления

```bash
git pull
bundle exec kamal deploy
```

Собирается новый образ, применяются миграции, трафик переключается после того, как новый
контейнер ответил на `/up`. Простоя при этом нет, но **во время игры обновляться не стоит**:
команды на дистанции ловят разрыв в самый неудачный момент.

## Переменные окружения

| Переменная | Обязательна | Что делает |
|---|---|---|
| `SECRET_KEY_BASE` | да | подпись сессионных cookies. Без неё production не стартует |
| `DATABASE_URL` | да | подключение к PostgreSQL |
| `APP_HOST` | да | домен для ссылок в письмах |
| `SMTP_ADDRESS`, `SMTP_PORT` | да | SMTP-сервер |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | да | учётные данные SMTP |
| `MAIL_FROM` | да | адрес отправителя |
| `RAILS_ENV` | да | `production` |
| `TZ` | нет | часовой пояс экземпляра. Игрок может выбрать свой в профиле |
| `DEFAULT_LOCALE` | нет | язык по умолчанию, по умолчанию `ru` |

Про `MAIL_FROM`: многие почтовые службы не дают отправлять от произвольного адреса и молча
подменяют заголовок `From` на адрес, под которым вы аутентифицировались. Если письма уходят «не
от того» — дело почти наверняка в этом, а не в приложении.

## Если что-то пошло не так

| Симптом | Где искать |
|---|---|
| Не выдаётся сертификат | A-запись домена не указывает на сервер, или 80/443 закрыты снаружи |
| Приложение не стартует, в логе `Missing secret_key_base` | не передан `SECRET_KEY_BASE` |
| Развёртывание висит на проверке здоровья | приложение не отвечает на `/up` — смотрите `kamal app logs` |
| Приложение не видит базу | в `DATABASE_URL` должно быть имя контейнера базы, а не `127.0.0.1` |
| Домен перестал открываться после деплоя | его нет в `proxy.host`; добавленное руками на сервере не переживает развёртывание |
| Письма не приходят | проверьте SMTP-переменные и то, что отправитель совпадает с логином |
| Регистрация отвечает «Слишком много попыток» | сработало ограничение по IP. Настраивается в «Администрирование → Настройки ограничений» |
