# Withdrawal Stops Play Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Withdrawing a game stops play, records why, and tells the teams.

**Architecture:** `Game#withdraw!` takes a category, an optional note and a mode — `freeze` keeps
runs intact and stops the clock by reusing `pause!`, `ended` closes every in-progress run.
`GamePassingsController` renders the reason in place of the play screen and refuses every
state-changing action.

**Tech Stack:** Rails 8.0, Ruby 3.3.12, SQLite in dev/test and PostgreSQL in production, RSpec,
Cucumber (Russian Gherkin), seven locales.

**Spec:** `docs/superpowers/specs/2026-08-19-withdrawal-stops-play-design.md`

## Global Constraints

- **Ruby is not on `PATH` in non-login shells.** Every session starts with
  `export PATH="$HOME/.rbenv/bin:$HOME/.rbenv/shims:$PATH"`.
- **Hash rockets** (`:key => value`) in application code; match the surrounding file.
- **Never edit any `features/**/*.feature` file** — a byte-identical acceptance contract of
  **228 scenarios / 2325 steps**. The play screen is the most heavily driven surface in it.
- **All seven locales** for every new key: `ru`, `en`, `uk`, `ka`, `tr`, `be`, `pl`.
  `spec/i18n_spec.rb` enforces exact `ru`↔`en` parity and only a **subset** check for the other
  five, so a key missing from the last five leaves the suite green.
- **The operator's note is operator-authored content: render it verbatim, never through `t()`,**
  and never `html_safe`/`raw`.
- **Turkish and Georgian**: a case suffix must never attach to an interpolated value. The notice
  renders the category and the note as **separate elements**, never composed into one sentence —
  which sidesteps the problem rather than solving it per language.
- **No Turbo and no rails-ujs.** `data: { confirm: ... }` is inert; `link_to ... :method => :post`
  does nothing. Views drive state changes with `button_to` or a real form.
- **`db/schema.rb` is regenerated by running the migration**, never hand-edited.
- **Migration timestamps**: `master` holds `20260819120000`, and the open D-scope cleanup PR claims
  `20260819130000`. This plan uses `20260819140000` so the two can merge in either order.
- **`create_user` takes no arguments**; **`create_team(options)` takes `:captain` and `:members`**;
  **`create_game_passing` calls `create_team` with no options, so its team has no captain.**
- **A request spec without `set_game_schedule!` gets 401s** — `starts_at` lives on `game_runs`, not
  `games`, and defaults to 2099. **Every negative assertion needs a positive status assertion beside
  it**; three examples in the preceding sub-projects passed on error responses without one.
- **Render every composed validation sentence before trusting it.** Nothing here tests that two
  separately-correct fragments make one correct sentence, and it has caught out four changes.
- TDD: the failing test first, watch it fail for the stated reason, then implement.

```ruby
class AddWithdrawalReasonToGames < ActiveRecord::Migration[8.0]
  def change
    # Nullable: they describe the CURRENT withdrawal and are cleared on
    # restore. A game withdrawn twice keeps no record of the first -- the audit
    # log does.
    add_column :games, :withdrawal_category, :string
    add_column :games, :withdrawal_note,     :text
    add_column :games, :withdrawal_mode,     :string

    # Whether THIS withdrawal paused the run. Without it, restore cannot tell a
    # pause it caused from one the operator made before withdrawing, and would
    # either double-count the held interval or un-pause a game the operator
    # meant to stay paused.
    add_column :games, :withdrawal_paused_run, :boolean, :null => false, :default => false
  end
end
```

and replace `withdraw!`/`restore!` (currently `:281-287`), keeping the `update_column` comment
above them — it explains why these bypass validation and it still applies:

```ruby
  # freeze  -- "stop, we are fixing this": runs stay intact and the clock stops.
  # ended   -- "this game is over": every run in progress closes, results stand.
  #
  # The mode is the operator's choice rather than a fixed policy, because only
  # the person pulling the game knows which event this is.
  #
  # Transactional: a withdrawal that paused the run but failed to record that
  # it did would leave restore! unable to tell its own pause from the
  # operator's, and nothing downstream could recover the difference.
  def withdraw!(category:, mode:, note: nil)
    raise ArgumentError, "unknown category" unless WITHDRAWAL_CATEGORIES.include?(category)
    raise ArgumentError, "unknown mode"     unless WITHDRAWAL_MODES.include?(mode)

    transaction do
      paused_by_withdrawal = false

      if mode == "freeze" && !self.paused?
        pause!
        paused_by_withdrawal = true
      end

      # THE GAME's passings, not the current run's, and in_progress rather than
      # finished_at nil -- both for the reasons resume! records at the same
      # association.
      game_passings.in_progress.find_each(&:end!) if mode == "ended"

      update_columns(:withdrawn_at           => Time.now,
                     :withdrawal_category    => category,
                     :withdrawal_note        => note,
                     :withdrawal_mode        => mode,
                     :withdrawal_paused_run  => paused_by_withdrawal)
    end
  end

  # Resumes ONLY a pause this withdrawal caused. An operator who paused before
  # withdrawing expects the game to still be paused afterwards.
  #
  # Ended runs are NOT revived. A game withdrawn-and-ended and then restored is
  # a game with a finished field; reinstating a team is an existing audited
  # intervention, and doing it implicitly here would resurrect runs the
  # operator deliberately closed.
  def restore!
    transaction do
      resume! if self.withdrawal_paused_run && self.paused?

      update_columns(:withdrawn_at           => nil,
                     :withdrawal_category    => nil,
                     :withdrawal_note        => nil,
                     :withdrawal_mode        => nil,
                     :withdrawal_paused_run  => false)
    end
  end
```

**Interfaces:**
- Consumes: `Game#withdrawn?`, `withdrawal_category`, `withdrawal_note`.

**A withdrawn game must not be a 401.** A refusal tells a team standing in the rain that they are
not authorised, which is both false and useless. A `GET` of the play screen succeeds and renders the
notice; state-changing actions are refused by redirecting back to it, so the team lands on the
explanation rather than an error.

```ruby
describe "playing a game that has been withdrawn", type: :request do
```

- [ ] **Step 3: Add the halt**

In `app/controllers/game_passings_controller.rb`, **immediately before** `find_or_create_game_passing`
(currently line 38) — the position matters and is not cosmetic. That filter *creates* a passing when
the team has none, so running the halt after it would enrol a team in a withdrawn game merely for
looking at the notice, and they would find themselves mid-run when it was restored. `@game` is set
by `find_game`, the first filter, and the notice needs nothing else.

```ruby
  # A withdrawn game is NOT a 401. A refusal tells a team standing in the rain
  # that they are not authorised, which is both false and useless -- and this
  # is the only notification mechanism the app has: no Turbo, no rails-ujs, no
  # polling, so a team learns on their next request. The GET therefore succeeds
  # and explains itself; the state-changing actions land them on that same
  # explanation rather than on an error.
  before_action :halt_if_withdrawn, except: [ :index, :show_results ]
```

and the method itself, in the controller's `private` section:

```ruby
  def halt_if_withdrawn
    return unless @game.withdrawn?

    if request.get?
      render "game_passings/withdrawn"
    else
      redirect_to show_current_level_path(:game_id => @game.id)
    end
  end
```
