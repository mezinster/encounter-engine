# Installation

How to run your own encounter-engine instance. Two paths, and the first is where to start:

- **[Trying it on your own machine](#trying-it-on-your-own-machine)** — half an hour, nothing to buy.
- **[A real installation](#a-real-installation)** — your domain, your server, real games.

User manual: [en.md](en.md). Русская версия: [deployment.ru.md](deployment.ru.md).
Will it cope with a game night? [performance.en.md](performance.en.md).

If you don't need a server of your own and just want to play, there is a
[shared one](https://game.mezin.eu/). Installing is for people who want their own domain, their
own rules and their own data.

---

## What this application is

An ordinary Ruby on Rails 8 application. Nothing exotic: no job queue, no Redis, no background
workers, no frontend build — static files are served straight from `public/`. One `puma` process
and one database.

| | |
|---|---|
| Ruby | 3.3.12 (pinned in `.ruby-version` and `Gemfile`) |
| Database | sqlite in development, PostgreSQL in production |
| Mail | any SMTP server |
| What has to face the world | HTTP(S) on 80 and 443 |

Mail is not a nicety here: teams are formed by e-mailed invitation, and the signup password is
generated by the server and sent by mail. Without working SMTP the instance will boot and will
not be usable.

## Trying it on your own machine

This is the "see how it works" path. Sqlite instead of PostgreSQL, no mail actually delivered,
no HTTPS.

**1. Ruby 3.3.12**, installed via rbenv. In non-login shells rbenv may not be on `PATH`, in
which case prefix your commands with:

```bash
export PATH="$HOME/.rbenv/bin:$HOME/.rbenv/shims:$PATH"
```

**2. Dependencies and database:**

```bash
bundle install
bin/rails db:setup
```

`db:setup` creates `db/development.sqlite3` from `db/schema.rb`. The database files are not in
the repository — they are built locally.

**3. Run it:**

```bash
bin/rails server
```

The application is on `http://localhost:3000`.

**4. Your first user.** Sign up through the form — you are signed in immediately afterwards.

> **Development delivers no mail at all** (`config.action_mailer.delivery_method = :test`). The
> password the server generated at signup is nowhere you can read it, so you will not be able to
> sign in again. Set yourself one from the console:
>
> ```bash
> bin/rails console
> ```
> ```ruby
> User.find_by(nickname: "yournick").update!(password: "secret", password_confirmation: "secret")
> ```

**5. Make yourself an administrator** — see [The first administrator](#6-the-first-administrator).

**6. The test suites**, if you want to confirm nothing is broken:

```bash
bundle exec rspec
bundle exec cucumber
```

## A real installation

Deployment is [Kamal 2](https://kamal-deploy.org/): a Docker image is built, pushed to a
registry and run on your server over ssh. The proxy, Let's Encrypt certificates and the
container cutover are Kamal's job.

### What you need

| | |
|---|---|
| A server | Ubuntu, 1–2 vCPU, 2 GB RAM. Enough for a game with dozens of teams |
| A domain | with an A record pointing at the server — **before** the first deploy, or Let's Encrypt will not issue a certificate |
| Access | ssh by key, a user with `sudo` |
| An image registry | GitHub Container Registry, Docker Hub, anything |
| SMTP | address, port, username, password |
| On your own machine | Ruby with the project's gems (`bundle install`) and Docker to build the image |

Ports 80 and 443 must be reachable from outside. 5432 (PostgreSQL) must **not** be: in
`config/deploy.yml` it is published as `127.0.0.1:5432:5432`, which means it is reachable only
from the server itself. Do not change that to `0.0.0.0`.

### 1. Preparing the server

`ansible/` holds a small playbook: it installs Docker, adds the deploy user to the `docker`
group, creates the volume for PostgreSQL data and enables unattended security upgrades.

```bash
ansible-playbook -i ansible/inventory.ini ansible/playbook.yml
```

Put your own host in `ansible/inventory.ini`. Note that the playbook **deliberately does not
touch the firewall** — it assumes filtering happens outside the machine (a cloud security
group). If that is not your situation, open 22, 80 and 443 yourself.

All of this can be done by hand instead: what is needed is Docker, and a user allowed to run it.

### 2. `config/deploy.yml`

This is one specific instance's configuration, and in the repository it is filled in for the one
living at `game.mezin.eu`. What to change:

| Key | What to put there |
|---|---|
| `service` | your service name (it also prefixes container names) |
| `image` | `your-account/encounter-engine` |
| `servers.web` | your server's IP or hostname |
| `proxy.host` | your domain. Several, comma-separated, are fine — each gets a certificate |
| `registry.server` / `registry.username` | your image registry |
| `ssh.user` | the deploy user |
| `env.clear.APP_HOST` | **one** domain — the one that will appear in e-mailed links |
| `env.clear.TZ` | the server's timezone, e.g. `Europe/Vienna` |
| `env.clear.DEFAULT_LOCALE` | default language: `ru`, `en`, `uk`, `ka`, `tr`, `be` or `pl` |
| `accessories.db.image` | your PostgreSQL image (see below) |
| `accessories.db.host` | the same server |

Two things that are easy to get wrong:

- **`proxy.host` is the single source of truth about domains.** Kamal rebuilds its whole routing
  table on every deploy, and a host registered by hand on the server disappears silently at the
  next one.
- **`APP_HOST` is one domain, not a list.** Absolute links in e-mail are built from it. The
  application may answer on several domains, but mail must point people at one place.

### 3. The database

`accessories.db` runs PostgreSQL alongside the application, on the same server, with its data in
a named Docker volume.

The image is built from `Dockerfile.postgres`: stock `postgres:16` plus
[wal-g](https://github.com/wal-g/wal-g) for continuous backup, and tuning for a small server.
Nothing in the image is specific to any one cloud — where backups go is decided by environment
variables (`WALG_*`), and wal-g speaks S3, Azure Blob, GCS and plain filesystem.

If you don't want backups yet, plain `postgres:16` works — the application knows nothing about
wal-g. Just be aware that a database of game results with no backups lasts until the first
serious mistake.

The application reaches the database **by container name** (`<service>-db`), not `127.0.0.1`:
the containers share a Docker network, and loopback inside the app container leads back to the
app container, not to the database.

### 4. Secrets

There are no secret values in this repository and there must not be. `.kamal/secrets` only
**names** the variables; the values come from the environment of whoever runs the deploy:

```
SECRET_KEY_BASE=$SECRET_KEY_BASE
```

What you have to supply:

| Variable | What it is |
|---|---|
| `SECRET_KEY_BASE` | the key that signs session cookies |
| `POSTGRES_PASSWORD` | the database user's password |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | mail credentials |
| `SMTP_ADDRESS`, `SMTP_PORT` | your SMTP server |
| `KAMAL_REGISTRY_PASSWORD` | image registry token |

`DATABASE_URL` and `MAIL_FROM` are **composed** in `.kamal/secrets` from the values above rather
than set separately, so that the database password and the sender address each exist in exactly
one place.

Rules worth keeping:

- **`SECRET_KEY_BASE` is generated once** (`bin/rails secret`) and then left alone. Changing it
  signs everybody out at once. In production it has **no** fallback: the application refuses to
  boot without it, deliberately, so that no "temporary" default key can appear in a public
  repository.
- **Values live in the environment only.** A `chmod 600` file your shell sources, a password
  manager, or your CI's secrets. Not in a config file, not in shell history, not in chat.
- If a secret does leak, **revoke it** rather than planning to rotate it later.

### 5. The first deploy

```bash
bundle exec kamal setup
```

`setup` installs what the server needs, brings up the database, builds and pushes the image,
starts the application and obtains certificates. After that it is the ordinary:

```bash
bundle exec kamal deploy
```

Migrations run **by themselves**, as the container starts (`bin/docker-entrypoint` calls
`db:prepare`). There is no separate step for them, and on the first deploy the schema is created
from nothing.

Kamal checks the application's health at `/up`. Until that answers, traffic is not cut over to
the new container.

Useful:

```bash
bundle exec kamal app logs -f      # logs
bundle exec kamal app exec -i "bin/rails console"   # console
bundle exec kamal rollback         # go back to the previous image
```

> `kamal rollback` rolls back **the image, not the database**. If the release you are rolling
> back past carried a migration that dropped or renamed a column, the older image will not run
> against the newer schema. That is a property of this style of deployment generally, not of
> this application.

### 6. The first administrator

Nobody holds administrator rights until they are granted, and only another administrator can
grant them. The first one has to be appointed from the console:

```bash
bundle exec kamal app exec -i "bin/rails console"
```

```ruby
User.find_by(nickname: "yournick").update!(is_superadmin: true)
```

Everything after that happens in the interface: the **Administration** section of the left menu.

Two things worth knowing in advance:

- **The last administrator cannot be demoted** — not through the interface, not from the
  console. An instance must never be left with nobody able to run it.
- **Appointing from the console is not recorded in the action log.** The log is kept by the web
  application, and the console works around it. This is the one hole in the log, and it cannot
  be closed.

### 7. Backups

If you built the PostgreSQL image from `Dockerfile.postgres`, the server is already archiving
WAL continuously (`archive_command = 'wal-g wal-push %p'`) — but **base backups** still have to
be taken on a schedule, because WAL alone restores nothing.

`ops/host/` holds a ready systemd timer and service that do this on the host rather than inside
the container: Kamal recreates the database container on every deploy, so a schedule installed
inside it would vanish at the next release.

The restore procedure is [`docs/runbooks/restore.md`](../runbooks/restore.md). The important
part: **restore into a throwaway container first and look at what you got**, and only then touch
production. `ops/` has scripts for both steps.

### 8. Updating

```bash
git pull
bundle exec kamal deploy
```

A new image is built, migrations run, traffic moves over once the new container answers `/up`.
There is no downtime — but **don't deploy during a game**: teams out in the city hit the gap at
the worst possible moment.

### 9. Reclaiming file storage

Uploaded files count against a per-game quota and an instance cap, both adjustable in
`/admin/settings`. Two maintenance tasks exist for what that screen cannot do. Both run on the
server; neither has a button.

```bash
bundle exec kamal app exec 'bin/rails game_files:purge_orphans'
```

Deletes stored data attached to nothing. Orphans are left behind by uploads rejected part-way —
which happens most when the disk is already under pressure, so this is worth knowing about
before you need it.

**One caveat, recorded honestly.** The task has no age cutoff, unlike the version Rails' own
guides suggest. The reasoning is that this application has no direct uploads, so no other
connection can observe an upload in flight as unattached — but that is a reading of the upload
code, not an experiment, and nobody has run it against a server taking real simultaneous
uploads. Prefer to run it when nothing is being uploaded. If a second way of writing files is
ever added, re-check that reasoning first: the failure it would cause is a file purged from
under an author mid-upload, and it would be silent.

```bash
bundle exec kamal app exec 'bin/rails game_files:regenerate_variants'
```

Rebuilds every file's generated previews and rewrites the recorded size of them. Useful when the
stored usage figures have drifted from what is really on disk. Safe to re-run; one unreadable
file is reported and skipped rather than stopping the rest.

## Environment variables

| Variable | Required | What it does |
|---|---|---|
| `SECRET_KEY_BASE` | yes | signs session cookies. Production will not boot without it |
| `DATABASE_URL` | yes | PostgreSQL connection |
| `APP_HOST` | yes | the host used for links in e-mail |
| `SMTP_ADDRESS`, `SMTP_PORT` | yes | SMTP server |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | yes | SMTP credentials |
| `MAIL_FROM` | yes | sender address |
| `RAILS_ENV` | yes | `production` |
| `TZ` | no | the instance's timezone. A player can pick their own in their profile |
| `DEFAULT_LOCALE` | no | default language, `ru` if unset |

About `MAIL_FROM`: many mail providers will not send from an arbitrary address and silently
rewrite the `From` header to the account you authenticated as. If mail arrives "from the wrong
person", that is almost certainly why, not the application.

## When something goes wrong

| Symptom | Where to look |
|---|---|
| No certificate is issued | the domain's A record doesn't point at the server, or 80/443 are closed |
| Boot fails with `Missing secret_key_base` | `SECRET_KEY_BASE` was not passed through |
| The deploy hangs on the health check | the application isn't answering `/up` — read `kamal app logs` |
| The application can't see the database | `DATABASE_URL` must name the database container, not `127.0.0.1` |
| A domain stopped resolving after a deploy | it isn't in `proxy.host`; hand-registered hosts don't survive a deploy |
| Mail doesn't arrive | check the SMTP variables, and that the sender matches the account |
| Signup answers "too many attempts" | the per-IP rate limit fired. Tune it in Administration → Rate limits |
